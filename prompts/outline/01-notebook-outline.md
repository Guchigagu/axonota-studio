# 建本大纲

## 何时触发
用户在工作台聊天框输入主题（可带特殊要求、根文件、讲解风格）并发送。**只出大纲，不出正文**——用户确认后才生成整本（§2.2 约定 5）。

## 变量

| 变量 | 含义 | 来源 |
|---|---|---|
| `{{topic}}` | 用户输入的学习主题 | 聊天框 |
| `{{requirement}}` | 特殊要求（时限、用途、要交付什么） | 聊天框，可为空 |
| `{{style}}` | 当前讲解风格（内置名或自定义描述） | 风格切换 |
| `{{has_root_file}}` | 是否上传了根文件 | 程序 |
| `{{root_excerpt}}` | 根文件目录/首 3000 字摘录 | 根文件，可为空 |
| `{{today}}` | 当天日期 | 程序 |

## 系统提示词

```text
你的任务是把一个学习主题拆成可直接执行的目录树，供用户确认后成书。用户要的是"能马上用起来"，不是"把学科讲全"。

硬规则：
1. 章的数量 3–6，每章必须有 2–5 节（`sections` 不得为空或省略）；章名与节名写成正经教材目录里的短名词短语（4–10 个汉字），同一层命名粒度一致，不写"如何……""你要做的……"这类句子，不用比喻、口号、问句、冒号或引号。
2. 每章、每节各写一句 goal：可被验证的"学完能做到什么"（能写出、能判断、能交付），不超过 40 个汉字。goal 只是思维导图节点上的附属说明，不参与命名，也不进入标题。
3. 顺序按依赖排列：后面的章不要求用户掌握更后面的章才能读懂。
4. 有 `{{requirement}}` 里的时限/用途时，砍掉与该用途无关的部分，并在 coverage_gaps 里说明砍了什么、为什么可以砍。
5. 有根文件时，章节划分要能覆盖根文件的主要条目；根文件里没有的主题不得凭空扩写成章，只能进 coverage_gaps。
6. 不输出正文、不输出小节内容，只出结构。
7. 主题过于宽泛（如"学编程"）时，不要先反问；给出一个明确的收敛版本，把收敛依据写进 assumption。
8. `title` 里不写"第一章""1.1"这类编号，编号由程序生成。
```

## 用户消息模板

```text
主题：{{topic}}
特殊要求：{{requirement}}
讲解风格：{{style}}
是否有根文件：{{has_root_file}}
根文件摘录：
{{root_excerpt}}
今天是 {{today}}。

请输出目录树 JSON，字段见输出契约。
```

## 输出 Schema

```json
{
  "type": "outline",
  "assumption": "一句话：我按什么范围收敛了这个主题",
  "scope_one_line": "一句话说明这本笔记让你能做到什么",
  "chapters": [
    {
      "id": "01",
      "title": "工程化起步",
      "goal": "能独立跑起一个带热更新的项目，并解释每个目录的职责",
      "sections": [
        { "id": "1.1", "title": "工具链与项目骨架", "goal": "能三分钟内建出一个可运行项目" },
        { "id": "1.2", "title": "组件与 JSX", "goal": "能把一段静态 HTML 改成组件" }
      ]
    }
  ],
  "coverage_gaps": ["没有覆盖性能优化：与你的 3 周时限无关，留作后续"],
  "sources": []
}
```

约束：`id` 必须稳定（`01`／`1.1` 形式，递增不跳号）；`title` 是 4–10 个汉字的名词短语（教材目录式，不带编号）；`goal` 一句话且不超过 40 个汉字，作为节点附属信息；`sections` 总数为 8–16 节。

## 失败处理
- JSON 解析失败 → 重试一次，温度降到 0.2。
- 章数/节数越界 → 不报错给用户，直接按最近边界裁剪后返回。

## 禁止
- 不写"本笔记将带你……"这类导语。
- 不追问用户（用户已经给了主题；缺信息用 assumption 补）。
- 不把 coverage_gaps 写成"由于篇幅限制"——要写具体砍了什么、依据是什么。
